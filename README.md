# rag-assistant-ai-service

Python / FastAPI microservice of the **Corporate RAG Assistant**, a portfolio project where users upload PDF documents and then ask natural-language questions about them. Answers are generated by an LLM based strictly on the uploaded content (Retrieval-Augmented Generation), instead of the model "making things up".

This service is the **Librarian**: it consumes document jobs from a queue, reads the PDFs, splits them into chunks and turns them into vectors so they can be searched by meaning. In Sprint 5 it will also retrieve the relevant chunks and ask the LLM (Groq / Llama 3) to answer.

## The system at a glance

| Repository | Role | Stack |
|---|---|---|
| [`rag-assistant-api`](https://github.com/mendesx5/rag-assistant-api) | **Front Desk**: REST API, uploads, persistence, publishes processing jobs | Java 17, Spring Boot |
| **`rag-assistant-ai-service`** (this repo) | **Librarian**: consumes jobs, reads PDFs, builds the vector index (answers questions in Sprint 5) | Python, FastAPI |
| [`rag-assistant-infra`](https://github.com/mendesx5/rag-assistant-infra) | Shared infrastructure | Docker Compose, PostgreSQL, RabbitMQ |

```
Client → rag-assistant-api → RabbitMQ → rag-assistant-ai-service → ChromaDB (→ Groq LLM in Sprint 5)
               ↓
          PostgreSQL
```

## What it does today

1. Starts a FastAPI app and, in the background, a RabbitMQ consumer on `documents.queue`.
2. For each message: validates the contract, reads the PDF from the path in the message and extracts its text.
3. Confirms (ACK) the message only after the work succeeded.

Already implemented as independent, tested modules: **chunking** (overlapping text chunks) and **local multilingual embeddings**. Coming next (Sprint 4): store the vectors in ChromaDB, wire the full pipeline into the consumer and report back to the API that the document was indexed.

## Getting started

Prerequisites: Python 3.10+ and the shared infrastructure running (see [`rag-assistant-infra`](https://github.com/mendesx5/rag-assistant-infra): `docker compose up -d`).

```bash
git clone https://github.com/mendesx5/rag-assistant-ai-service.git
cd rag-assistant-ai-service

python -m venv .venv
.venv\Scripts\activate          # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env            # Windows: copy .env.example .env
uvicorn app.main:app --reload
```

- Health check: <http://localhost:8000/health>
- Interactive API docs: <http://localhost:8000/docs>
- The first time embeddings are generated, the model (~220 MB) is downloaded into `.model_cache/`.

### Configuration

Settings are read from environment variables or from `.env`.

| Variable | Default | Description |
|---|---|---|
| `RABBITMQ_HOST` | `localhost` | RabbitMQ host |
| `RABBITMQ_PORT` | `5672` | RabbitMQ AMQP port |
| `RABBITMQ_USER` | `guest` | RabbitMQ user |
| `RABBITMQ_PASSWORD` | `guest` | RabbitMQ password |
| `RABBITMQ_QUEUE` | `documents.queue` | Queue to consume |
| `CHUNK_SIZE` | `1000` | Maximum characters per chunk |
| `CHUNK_OVERLAP` | `200` | Characters repeated between consecutive chunks |
| `EMBEDDING_MODEL` | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` | Local embedding model |
| `EMBEDDING_CACHE_DIR` | `.model_cache` | Where the model is stored |

## Messaging contract

The service consumes the messages published by `rag-assistant-api`:

| | |
|---|---|
| Exchange | `documents.exchange` (direct, durable), declared by the API |
| Queue | `documents.queue` (durable) |
| Routing key | `documents.uploaded` |

```json
{
  "event_id": "UUID, unique per message",
  "document_id": "UUID of the stored document",
  "file_path": "absolute path of the stored PDF",
  "timestamp": "2026-10-27T15:00:00Z"
}
```

The queue is declared here with exactly the same properties as in the API. A mismatch makes RabbitMQ refuse the connection (`PRECONDITION_FAILED`).

## How messages are handled

The consumer uses **manual acknowledgements** and `prefetch_count=1`: RabbitMQ delivers one message at a time and keeps it as "unacknowledged" until the work is done. If the service dies mid-processing, the message goes back to the queue.

| Situation | Action | Why |
|---|---|---|
| Processing succeeded | `ack` | Safe to forget the message |
| Invalid message or unreadable PDF (irreversible) | `nack`, no requeue | Retrying can never fix it |
| Unexpected error | `nack`, requeue | May be temporary |

PDF reading runs in a worker thread so the event loop stays responsive.

## Design decisions

- **Manual ack + prefetch 1.** No message is lost if the service crashes, and work is distributed fairly if more consumers are added.
- **Irreversible vs unexpected errors.** Custom exceptions let the consumer decide whether a retry makes sense.
- **Local multilingual embeddings.** No API key or cost, and it handles Portuguese documents (the default ChromaDB model is English-focused). Indexing and querying must use the same model.
- **`Embedder` interface.** Components depend on an abstraction, so tests use a fake embedder and the model can be replaced without touching the rest.
- **Overlapping chunks.** Splitting respects paragraphs and sentences when possible, and the overlap keeps context across cut points.
- **Everything configurable through the environment**, with sensible defaults.

## Known limitations

- Scanned PDFs (images) have no extractable text; they would need OCR, which is out of scope for now.
- Messages that fail irreversibly are discarded until the Dead Letter Queue is added (Sprint 6). An unexpected, permanent error would be retried in a loop until then.
- The PDF is read from the local path in the message, so this service must share a filesystem with the API.

## Why two repositories

Java and Python live in separate repositories on purpose: it mirrors how the two services are meant to scale, deploy and evolve independently in a real microservices setup, instead of coupling them in a single deployable unit.
